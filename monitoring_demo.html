What are Prometheus and Grafana?

When you deploy a machine-learning service in production, you need to answer questions like: "Is it responding? How fast? Is the model drifting? Are requests failing?" Prometheus and Grafana answer those questions — together they form the industry-standard open-source monitoring stack.

Prometheus Time-Series Database

Prometheus is a metrics collector and database. Every 15 seconds it visits your app's /metrics URL, reads a list of counters and measurements, and stores them with a timestamp. Over time this builds a history — like a continuous log of numbers — that you can query.

Grafana Visualization Layer

Grafana is a dashboard tool. It connects to Prometheus, runs queries (called PromQL), and draws the results as live graphs, gauges, and tables. Grafana never stores metrics itself — it just visualizes what Prometheus already collected.

The key mental model: Pull, not Push Most monitoring systems require your app to send data to a server. Prometheus does the opposite — it pulls data from your app. Your app just exposes a URL and waits. Prometheus comes to you.

Why does this matter for ML? With a normal web service you just watch error rates and latency. With ML you also watch model behavior: Are predictions drifting toward one label? Is confidence dropping? Are inputs suddenly much longer? These are early signals of data shift before accuracy collapses.

How Prometheus is Spun Up

Prometheus is not started by Python code. It is a separate process — a Go binary inside a Docker container — started entirely by Docker Compose. Here is exactly how it happens in this project, step by step.

Step 1 — docker-compose.yml defines three services

docker-compose.yml 
# Three containers, one command to start all of them:
#   docker compose up

services:

  # ── Your ML service ──────────────────────────────────────────────
  inference:
    build: .                  # Build from your Dockerfile
    ports:
      - "8000:8000"           # Exposed to your laptop on port 8000
    environment:
      MODEL_PATH: ${MODEL_PATH:-/bert_model}

  # ── Prometheus ───────────────────────────────────────────────────
  prometheus:
    image: prom/prometheus:v2.54.0   # Official Docker image — no code to write
    ports:
      - "9090:9090"               # UI available at localhost:9090
    volumes:
      # Mount our config file INTO the container at the path Prometheus expects
      - ./monitoring/prometheus/prometheus.yml:/etc/prometheus/prometheus.yml:ro
    command:
      - "--config.file=/etc/prometheus/prometheus.yml"
      - "--storage.tsdb.retention.time=7d"  # Keep 7 days of history

  # ── Grafana ──────────────────────────────────────────────────────
  grafana:
    image: grafana/grafana:11.2.0
    ports:
      - "3000:3000"               # UI available at localhost:3000
    depends_on:
      - prometheus              # Wait for Prometheus to start first

Step 2 — prometheus.yml tells Prometheus what to scrape

This file is the entire Prometheus configuration for this project. It answers one question: "Where do you go to collect metrics, and how often?"

monitoring/prometheus/prometheus.yml 
global:
  scrape_interval: 15s       # Visit every target every 15 seconds
  evaluation_interval: 15s  # Evaluate alerting rules every 15 seconds

scrape_configs:
  - job_name: inference-service
    static_configs:
      - targets: ["inference:8000"]
        # "inference" is the Docker Compose service name —
        # Docker's internal DNS resolves it to the container's IP.
        # No hard-coded IP address needed.
    metrics_path: /metrics    # The URL path to hit on each target
Why "inference:8000" and not "localhost:8000"? Prometheus and the inference service are in separate containers. Each container has its own network namespace — "localhost" inside Prometheus refers to Prometheus itself, not your Python app. Docker Compose creates a shared virtual network and gives each service a DNS name equal to its service name. So inference resolves to the inference container's IP automatically.

Step 3 — Python exposes the /metrics endpoint

The Python app does not start Prometheus. It just registers metrics objects and exposes a URL that Prometheus can pull from. The entire integration is three things in app/main.py:

app/main.py (relevant lines only) 
# 1. Import the metric types you want to track
from prometheus_client import Counter, Histogram, generate_latest, CONTENT_TYPE_LATEST

# 2. Declare global metric objects (registered automatically in a global registry)
PREDICTION_COUNT = Counter(
    "bert_predictions_total",   # metric name
    "BERT predictions by label",  # human description
    ["label", "model_version"],   # label dimensions
)

REQUEST_LATENCY = Histogram(
    "http_request_duration_seconds",
    "HTTP request latency",
    ["method", "endpoint"],
)

# 3. Expose a /metrics endpoint — Prometheus calls this every 15 seconds
@app.get("/metrics")
async def metrics():
    # generate_latest() serializes every registered metric into
    # the plain-text format Prometheus understands.
    return Response(generate_latest(), media_type=CONTENT_TYPE_LATEST)

Summary — who does what

  • Docker Compose — starts three containers: inference, prometheus, grafana. Handles networking, volumes, environment variables, startup order.
  • Prometheus binary (inside its container) — reads its config file, then every 15 seconds calls http://inference:8000/metrics and stores the result in its time-series database.
  • Python app — registers metric objects at startup. Increments counters and records histograms as requests come in. Exposes /metrics so Prometheus can read them.
  • Grafana — reads from Prometheus via PromQL queries. Draws graphs. Auto-provisioned with our datasource and dashboard from monitoring/grafana/.

Anatomy of the /metrics Endpoint

Open http://localhost:8000/metrics in your browser after running docker compose up. You'll see plain text. This is the Prometheus exposition format — a simple text protocol that every monitoring-aware service speaks. Here is what each section means.

Part A — Python Runtime Metrics (free, automatic)

The prometheus_client library registers these automatically just by being imported. You write zero code for them. 

# HELP python_gc_objects_collected_total Objects collected during gc
# TYPE python_gc_objects_collected_total counter
python_gc_objects_collected_total{generation="0"} 357.0
python_gc_objects_collected_total{generation="1"} 33.0
python_gc_objects_collected_total{generation="2"} 0.0

# HELP process_resident_memory_bytes Resident memory size in bytes
# TYPE process_resident_memory_bytes gauge
process_resident_memory_bytes 8.60454912e+08
Line-by-line: # HELP is the human description. # TYPE declares whether this is a counter, gauge, or histogram. The data line is: metric_name{label="value"} number.

process_resident_memory_bytes 8.60454912e+08 means the Python process is using ~860 MB of RAM — that's our BERT model loaded into memory.

Part B — HTTP Request Metrics (MetricsMiddleware)

These come from app/middleware/metrics.py. Every HTTP request — whether /health, /v1/classify, or /metrics itself — gets counted and timed. 

# HELP http_requests_total Total HTTP requests
# TYPE http_requests_total counter
http_requests_total{endpoint="/health",method="GET",status_code="200"} 3.0
http_requests_total{endpoint="/v1/classify",method="POST",status_code="200"} 12.0
http_requests_total{endpoint="/metrics",method="GET",status_code="200"} 8.0

# HELP http_request_duration_seconds HTTP request latency
# TYPE http_request_duration_seconds histogram
http_request_duration_seconds_bucket{endpoint="/v1/classify",method="POST",le="0.005"} 0.0
http_request_duration_seconds_bucket{endpoint="/v1/classify",method="POST",le="0.01"}  0.0
http_request_duration_seconds_bucket{endpoint="/v1/classify",method="POST",le="0.025"} 0.0
http_request_duration_seconds_bucket{endpoint="/v1/classify",method="POST",le="0.05"}  8.0
http_request_duration_seconds_bucket{endpoint="/v1/classify",method="POST",le="0.1"}   12.0
http_request_duration_seconds_bucket{endpoint="/v1/classify",method="POST",le="+Inf"}  12.0
http_request_duration_seconds_sum{endpoint="/v1/classify",method="POST"} 0.732
http_request_duration_seconds_count{endpoint="/v1/classify",method="POST"} 12.0
Labels in curly braces — endpoint="/v1/classify" method="POST" status_code="200" — let you filter and group in PromQL. Each unique combination is its own time series.

Histogram buckets (le = "less or equal"): 8 out of 12 requests finished in ≤50ms. All 12 finished in ≤100ms. The _sum (total seconds) divided by _count (total requests) gives you the average latency: 0.732 / 12 = 61ms.

Part C — Model-Specific Metrics (app/main.py)

These are custom metrics we defined ourselves. They track what the model is doing, not just HTTP traffic. 

# HELP bert_predictions_total BERT predictions by label
# TYPE bert_predictions_total counter
bert_predictions_total{label="positive",model_version="v1"} 8.0
bert_predictions_total{label="negative",model_version="v1"} 4.0

# HELP bert_confidence Softmax confidence of the predicted class
# TYPE bert_confidence histogram
bert_confidence_bucket{model_version="v1",le="0.5"}  0.0
bert_confidence_bucket{model_version="v1",le="0.6"}  0.0
bert_confidence_bucket{model_version="v1",le="0.7"}  0.0
bert_confidence_bucket{model_version="v1",le="0.8"}  1.0
bert_confidence_bucket{model_version="v1",le="0.9"}  3.0
bert_confidence_bucket{model_version="v1",le="0.95"} 6.0
bert_confidence_bucket{model_version="v1",le="0.99"} 12.0
bert_confidence_bucket{model_version="v1",le="+Inf"} 12.0
bert_confidence_sum{model_version="v1"}   11.28
bert_confidence_count{model_version="v1"} 12.0

# HELP bert_input_tokens Tokenized input length per classify request
# TYPE bert_input_tokens histogram
bert_input_tokens_bucket{model_version="v1",le="16"}  0.0
bert_input_tokens_bucket{model_version="v1",le="32"}  2.0
bert_input_tokens_bucket{model_version="v1",le="64"}  7.0
bert_input_tokens_bucket{model_version="v1",le="128"} 12.0
bert_input_tokens_bucket{model_version="v1",le="+Inf"} 12.0
bert_predictions_total — 8 positive, 4 negative. If this ratio suddenly shifts to 100% positive, something upstream changed (new client, bad text cleaning, label flip).

bert_confidence — all 12 predictions fell between 0.95 and 0.99 confidence. A well-trained BERT on clear inputs should sit up here. If the distribution creeps below 0.7, the model is seeing inputs that look unlike its training data — early warning of data drift.

bert_input_tokens — all inputs were ≤128 tokens. Our model truncates at 128, so if inputs start landing in the 256+ buckets it means we're silently cutting off content and accuracy will drop invisibly.

Part D — Why Some Metrics Look Empty

# HELP inference_requests_total Total inference requests
# TYPE inference_requests_total counter
# (no data lines here yet)
No lines after the TYPE header means zero observations so far. The inference_requests_total counter is only incremented by the global exception handler — it fires when an unhandled error occurs. If your service has had no errors, this section is empty. That is good.
Quick test: generate some traffic Run this in a terminal, then refresh localhost:8000/metrics to see the counters go up:

curl -X POST localhost:8000/v1/classify -H "Content-Type: application/json" -d '{"text":"I loved this movie!"}'

PromQL Commands to Run in Prometheus

Open http://localhost:9090, click the Graph tab, paste any query below into the search box, and press Enter. Switch between Table (current value) and Graph (history over time) using the tabs above the result.

Group A — Traffic & Request Rates

What You Want to KnowPromQL QueryNotes
Requests per second (all endpoints) rate(http_requests_total[1m]) rate() computes per-second average over the last 1 minute. Without this, counters only ever go up and are hard to read as a graph.
Requests/sec to /v1/classify only rate(http_requests_total{endpoint="/v1/classify"}[1m]) Curly braces filter by label value.
Total requests ever (raw counter) http_requests_total Just the current value of the counter — no rate. Use Table view.
Requests/sec grouped by status code sum by(status_code) (rate(http_requests_total[1m])) sum by() collapses all other labels and keeps only status_code, so you get one line per status.

Group B — Latency Percentiles

Average latency hides problems — one slow request in 1000 barely moves the average. Percentiles (p50, p95, p99) tell you what most users experience.

What You Want to KnowPromQL QueryNotes
p50 latency (median) histogram_quantile(0.50, rate(http_request_duration_seconds_bucket{endpoint="/v1/classify"}[5m])) Half of requests are faster than this. The typical user experience.
p95 latency histogram_quantile(0.95, rate(http_request_duration_seconds_bucket{endpoint="/v1/classify"}[5m])) 95% of requests finish below this. Your "normal slow" baseline.
p99 latency histogram_quantile(0.99, rate(http_request_duration_seconds_bucket{endpoint="/v1/classify"}[5m])) 99% of requests finish below this. Your worst-case users.
Average latency (simple arithmetic) rate(http_request_duration_seconds_sum{endpoint="/v1/classify"}[5m]) / rate(http_request_duration_seconds_count{endpoint="/v1/classify"}[5m]) Sum / count = average. Hides outliers — prefer p95/p99.

Group C — Error Rate

What You Want to KnowPromQL QueryNotes
5xx error rate (requests/sec) rate(http_requests_total{status_code=~"5.."}[1m]) =~ is a regex match — 5.. matches 500, 503, etc.
Error rate as % of total 100 * sum(rate(http_requests_total{status_code=~"5.."}[1m])) / sum(rate(http_requests_total[1m])) Alerts typically fire at >1% for critical services.

Group D — Model Behavior (BERT-specific)

What You Want to KnowPromQL QueryNotes
Predictions per second by label sum by(label) (rate(bert_predictions_total[1m])) Watch positive/negative ratio. A sudden shift means your input distribution changed.
Total predictions ever bert_predictions_total Raw counter — use Table view to see positive vs. negative split.
Median confidence histogram_quantile(0.50, rate(bert_confidence_bucket[5m])) A well-calibrated BERT sits near 0.95–0.99. Dropping below 0.8 signals model/data mismatch.
p99 confidence histogram_quantile(0.99, rate(bert_confidence_bucket[5m])) Even your most uncertain predictions — if this dips to 0.5 the model is basically guessing.
Median input token length histogram_quantile(0.50, rate(bert_input_tokens_bucket[5m])) If median crosses 128 it means inputs are being truncated silently.
Is the model drifting? (ratio test) bert_predictions_total{label="positive"} / ignoring(label) bert_predictions_total{label="negative"} Returns how many positives per negative. In balanced data this should be near 1.0.

Group E — System & Prometheus Meta

What You Want to KnowPromQL QueryNotes
Python process memory (MB) process_resident_memory_bytes / 1024 / 1024 PromQL supports arithmetic. BERT in memory is ~860 MB.
Is the inference service up? up{job="inference-service"} 1 = Prometheus can reach /metrics. 0 = it's down or the scrape failed.
When was the last scrape? scrape_duration_seconds{job="inference-service"} How long the last scrape took. Should be milliseconds.
All metrics for this job {job="inference-service"} Wildcard — returns every time series Prometheus has for this target. Good for exploration.
Time window matters [1m] gives a reactive, noisy graph. [5m] smooths it out. [1h] shows trends. For dashboards, [5m] is usually best. For alerting, [1m] catches problems faster.
Grafana does all of this visually Everything above runs in localhost:9090. But in localhost:3000 (Grafana) the same queries are wired to live-updating graphs. Log in with admin / admin, then open Dashboards → inference. Each panel shows its PromQL query in the "Edit" view — use that to learn how the visualizations are built.
